BASICS TO LEARN FIRST
============================================================

UML
- UML means Unified Modeling Language. It provides standard diagrams for describing a software system.
- Different diagrams answer different questions. A class diagram describes structure. An activity diagram describes work. A sequence diagram describes messages over time.

Use case diagram
- An actor is a role outside the software, such as Student or Admin. It can also be another system.
- A use case is a service or goal, such as Pay Fees. It appears as an oval.
- The system boundary is the rectangle that separates the software's services from its external actors.
- A solid actor-use case line means that the actor participates in that service. It does not specify execution order.
- An include relationship means that the base use case requires the included behaviour. Its dashed arrow points to the included use case.
- An extend relationship adds behaviour under a condition. Its dashed arrow points from the additional use case to the base use case.
- Login can be a required step or a precondition. It does not have to be connected to every oval in a high-level diagram.

Class diagram
- A class describes a kind of object, such as Book or Payment.
- Attributes store its data. Operations describe what it can do.
- A class box normally has a name, an attribute compartment and an operation compartment.
- An association connects related classes. Its label describes the relationship.
- Multiplicity tells how many objects may be connected. Read the number near one end for one object at the opposite end.
- 1 means exactly one. 0..1 means optional, at most one. 0..* or * means any number, including zero. 1..* means one or more.
- Generalization means inheritance. The hollow triangle points at the general parent class.
- A plus sign usually means public visibility. A minus sign usually means private visibility.

Activity diagram
- An action is one step of work, such as Verify documents.
- The filled circle starts the activity. The bull's-eye activity-final node ends the entire activity.
- Arrows show control flow, meaning which step can happen next.
- A decision diamond chooses a path. A guard, such as [payment successful], says when a path is taken.
- A merge joins alternative paths. It does not wait for several parallel actions.
- Swimlanes group actions by responsibility. They do not create separate processes by themselves.

State machine diagram
- A state describes the condition of one object during its life, such as Scheduled or Cancelled.
- A transition moves the object to another state when an event occurs.
- The initial node starts the lifecycle. A final node means that the lifecycle being modelled has ended.
- State names describe conditions. Arrow labels describe events or conditions that cause changes.
- A retry arrow means an object can revisit an earlier state.

Sequence diagram
- Each participant has a lifeline. The vertical direction represents time, read from top to bottom.
- A message arrow shows one participant communicating with another.
- A narrow activation rectangle shows a period of execution. It is not stored data.
- A synchronous call normally waits for its operation to finish. A return message carries a result back, often drawn dashed.
- An alt frame separates alternative scenarios. Only the branch whose guard is true is followed.
- Do not read a payment-failure branch as occurring after the successful delivery. They are alternatives, even when message numbers continue across the drawing.
- A self-message represents internal work by the same participant.

Communication diagram
- Objects and their connecting links are the main focus, rather than vertical time.
- Numbered message arrows establish order. Follow 1, 2, 3 and so on.
- A link means that the connected participants can communicate. An arrow's direction identifies the sender and receiver of a particular message.
- Sequence and communication diagrams are both interaction diagrams. They can describe the same scenario using different layouts.

02. LIBRARY MANAGEMENT SYSTEM
Class Diagram
============================================================

PURPOSE AND TYPE
- This diagram describes the main library data objects and their relationships.
- A class diagram fits because the question asks for major classes and their relationships.

CLASSES AND MEMBERS
- Person stores common id, name and email values.
- Student adds rollNo and department. Student is a specialized Person.
- Librarian adds employeeId. Librarian is also a specialized Person.
- Book stores isbn, title, author and status. isAvailable() checks whether it can be issued.
- BookIssue records issueId, issueDate, dueDate and returnDate. issueBook() starts a loan and returnBook() records its return.
- Reservation stores reservationId, reservationDate and status. reserveBook() creates a reservation and cancelReservation() cancels it.
- Fine stores fineId, amount and paid. calculateFine() works out the charge and payFine() records payment.

RELATIONSHIPS
- Student and Librarian inherit common Person details. In UML the inheritance triangles must point to Person.
- One Student can have zero or many BookIssue records. Each BookIssue belongs to one Student.
- One Book can appear in zero or many BookIssue records over time. Each issue record concerns one Book.
- One Student can make zero or many Reservations. Each Reservation is made by one Student.
- One Book can appear in zero or many Reservations. Each Reservation concerns one Book.
- One BookIssue may incur zero or one Fine. Each Fine belongs to one BookIssue.
- One Librarian manages zero or many BookIssue records. Each record is managed by one Librarian in this design.

EXAMPLE AND VIVA
- Issuing a book creates a BookIssue with a due date. Returning it sets returnDate. A late return can produce a Fine.
- Begin with this explanation. BookIssue represents a borrowing event, so the system can retain the history of a book and its borrower.
- A reservation is a request to borrow, while a BookIssue records an actual loan.
- This is a small model. Multiple physical copies of the same title can be represented with a separate BookCopy class in a larger design.

Class Diagram
============================================================

PURPOSE AND TYPE
- This diagram describes the objects used to register customers, select products, create orders, pay and deliver goods.

CLASSES AND MEMBERS
- Customer stores customerId, name, email and address. register() and login() support account access.
- Product stores productId, name, price and stock. search() represents finding products in this simple design.
- ShoppingCart stores cartId. addItem(), removeItem() and getTotal() manage a customer's current selections.

- Many CartItems may refer to the same Product. Each CartItem refers to one Product.
- One Customer places zero or many Orders. Each Order belongs to one Customer.
- Each Order has one Payment and one Delivery in this simplified design.
- An Order includes one or more Products.

CORRECTION NEEDED
- The saved Order-Product relationship has 1 next to Order and 1..* next to Product.
- That wrongly restricts each catalog Product to exactly one Order. The same product should be purchasable in many orders.
- Minimal fix is to change the multiplicity next to Order to 0..*. Keep 1..* next to Product.
- A fuller design uses OrderItem between Order and Product, with quantity and priceAtPurchase. This also preserves the price paid when the catalog price changes.
- The .vpp has not been edited during this recheck. Do not explain the incorrect 1 as a general e-commerce rule.

EXAMPLE AND VIVA
- A customer adds two units of a product to a CartItem, places an Order, makes a Payment and receives the Delivery.
- Begin with this explanation. The class diagram separates temporary cart selections from a placed order and connects the order to payment and delivery.
- The one-payment and one-delivery rules are classroom assumptions. Retries, partial payments and split shipments need a larger model.

05. ATM TRANSACTION SYSTEM
Activity Diagram
============================================================

PURPOSE AND TYPE
- This diagram follows an ATM session, including cash withdrawal and balance viewing.
- An activity diagram fits because the question asks for a workflow with decisions and alternative paths.

FLOW AND ELEMENTS
- The initial node leads to Insert card, Read card details and Enter PIN.
- The PIN decision sends a valid PIN to Display menu. An invalid PIN leads to Display invalid PIN message, then Eject card.
- The menu decision lets the user view the balance or enter a withdrawal amount.
- Display balance returns to Display menu. It does not force a withdrawal.
- Enter withdrawal amount leads to the funds decision.
- Sufficient funds lead to Dispense cash, Update account balance and Print receipt.
- Insufficient funds lead to Display insufficient funds message instead of cash dispensing.
- The successful withdrawal and insufficient-funds alternatives merge before Eject card.
- Eject card leads to the activity-final node.
- Each guard identifies the condition for taking an outgoing decision path. The merge joins alternatives, not parallel work.

EXAMPLE AND VIVA
- A user enters a valid PIN, selects withdrawal and enters an affordable amount. The ATM dispenses cash, updates the balance, prints a receipt and ejects the card.
- Begin with this explanation. This activity diagram shows the order of ATM actions and uses decisions for PIN validity, menu choice and sufficient funds.
- The model ends an invalid-PIN attempt by ejecting the card. Real ATMs may allow a limited number of retries or retain the card, but that policy is not modelled here.

06. RAILWAY RESERVATION SYSTEM
Activity Diagram
============================================================

PURPOSE AND TYPE
- This diagram follows a railway booking from searching trains to a confirmed ticket.
- It explicitly includes the two alternatives requested in the question, unavailable seats and failed payment.

MAIN FLOW
- Login starts the session.
- Enter source, destination and date supplies the search details.
- Search trains finds matching services. Select train and class identifies the desired journey.
- Check seat availability leads to a decision.
- If seats are available, Enter passenger details and Proceed to payment follow.
- The payment decision chooses success or failure.
- On success, Confirm ticket is followed by Generate PNR and e-ticket and Send confirmation to passenger.
- PNR means Passenger Name Record. Here it identifies the reservation record.

ALTERNATIVES AND RELATIONSHIPS
- If seats are unavailable, Display seats not available is followed by Offer waiting list or other trains. This attempt then ends.
- If payment fails, Display payment failure message is followed by Release held seats. The failed attempt does not produce a confirmed ticket.
- The alternatives join at a merge before the final node.
- Release held seats assumes the chosen seats were held during payment. An explicit Hold seats action would make that assumption clearer, but it is not a separate action in the saved diagram.

EXAMPLE AND VIVA
- A passenger finds a train with seats, enters passenger details and pays successfully. The system confirms the ticket and generates the PNR.
- Begin with this explanation. The diagram models the railway booking workflow and prevents seat-unavailable and payment-failed paths from reaching ticket confirmation.
- A waiting-list booking has its own rules. This diagram only offers that option and does not model the complete waiting-list lifecycle.

07. ONLINE BANKING APPLICATION
State Machine Diagram
============================================================

PURPOSE AND TYPE
- The object being modelled is one transaction, not the bank account itself.
- A state machine fits because the question asks how that transaction changes state.

STATES AND TRANSITIONS
- The initial node enters Initiated when a transaction starts.
- Initiated means the transaction has been created but is not authenticated yet.
- Submitting details moves it to Authenticating.
- Authenticating means the system is checking the user's identity or permission.
- Authentication success moves it to Processing. Authentication failure moves it to Failed.
- A user cancellation from Initiated or Authenticating moves it to Cancelled.
- Processing means the system is carrying out the transaction.
- Processing success moves it to Completed. Insufficient funds or another processing error moves it to Failed.
- Completed means the transaction succeeded. Failed means it did not succeed. Cancelled means the user stopped it before processing in this model.
- Completed, Failed and Cancelled lead to the final node for that transaction lifecycle.

EXAMPLE AND VIVA
- A transfer starts, the user authenticates, processing succeeds and the transaction becomes Completed.
- Begin with this explanation. This state machine shows one banking transaction moving through initiation, authentication and processing to a successful, failed or cancelled outcome.
- Cancellation is not shown during Processing. That avoids assuming that an already executing money transfer can simply be stopped.

08. HOSPITAL MANAGEMENT SYSTEM
State Machine Diagram
============================================================

PURPOSE AND TYPE
- The object is a patient appointment. The diagram follows its lifecycle, not every hospital activity.

STATES AND TRANSITIONS
- The initial node enters Requested when the patient requests an appointment.
- Requested means the request exists but no slot has been allotted.
- Slot allotment moves it to Scheduled. A rejected or cancelled request moves it to Cancelled.
- Scheduled means a slot has been assigned. Patient confirmation moves it to Confirmed.
- Confirmed means the patient has accepted the appointment.
- A change request from Scheduled or Confirmed moves it to Rescheduled.
- Rescheduled represents the change process. Allotting a new slot returns it to Scheduled, allowing confirmation of the new slot.
- Scheduled, Confirmed and Rescheduled can each move to Cancelled.
- A confirmed appointment moves to Completed when the patient visits the doctor, as labelled in this classroom model.
- Completed and Cancelled lead to the final node.

EXAMPLE AND VIVA
- A patient requests a visit, receives a slot and confirms it. If the slot changes, the appointment enters Rescheduled, receives a new slot and is confirmed again.
- Begin with this explanation. This state machine explains the conditions of an appointment and the events that schedule, confirm, reschedule, complete or cancel it.
- Scheduled and Confirmed are different because assigning a slot does not necessarily mean the patient has accepted it.
- In a more detailed system, arrival and consultation completion would be separate events. The saved diagram combines the visit into the completion transition.

- User initiates the transfer. Banking App receives requests. Authentication Service verifies access. Transaction Service coordinates account operations. Account DB stores account details and balances.
- The beneficiary is the recipient account. Debit reduces the sender's balance and credit increases the recipient's balance.

IMPROVEMENT TO MAKE EXPLICIT

- Authentication failure can also be shown in an outer alternative. The current interaction depicts successful login as its starting scenario.
- Debit and credit must be one atomic transaction in a real implementation. Either both commit or neither does. Separate arrows alone do not guarantee this.
- These improvements have not been applied to the .vpp during this recheck.

PURPOSE AND TYPE
- The object is one employee's payroll transaction for a payroll cycle.

16. VEHICLE RENTAL MANAGEMENT SYSTEM
Class Diagram
============================================================

PURPOSE AND TYPE
- This diagram identifies the six classes named in the question and their multiplicities.

CLASSES AND MEMBERS
- Customer stores customerId, name, phone and licenseNo. register() creates the customer record.
- Vehicle stores vehicleId, model, type, ratePerDay and available. checkAvailability() checks whether it can be rented.
- Booking stores bookingId, startDate, endDate and status. createBooking() and cancelBooking() manage reservations.
- Payment stores paymentId, amount, mode and date. makePayment() handles payment.
- RentalAgreement stores agreementId, terms, deposit and issueDate. generateAgreement() creates the agreement.
- Admin stores adminId and name. addVehicle(), removeVehicle() and manageBookings() support administration.

RELATIONSHIPS
- One Customer makes zero or many Bookings. Each Booking belongs to one Customer.
- One Vehicle is reserved in zero or many Bookings over time. Each Booking is for one Vehicle.
- Each Booking is paid through one Payment in this model.
- Each Booking is governed by one RentalAgreement in this model.
- One Admin manages zero or many Vehicles. Each Vehicle has one managing Admin.
- One Admin approves zero or many Bookings. Each Booking has one approving Admin in this design.

EXAMPLE AND VIVA
- A customer books a vehicle for three days. The booking connects that customer and vehicle with a payment and rental agreement, while an admin manages the vehicle and approves the booking.
- Begin with this explanation. Booking connects the renter, vehicle, payment and agreement, while Admin manages vehicles and booking approval.
- A vehicle's many bookings are across time, not permission for overlapping rentals. A no-overlap rule must be enforced separately.
- The one-payment and one-agreement multiplicities describe the simplified completed-booking view. Draft bookings, deposits and later balance payments need optional or multiple records in a fuller design.

18. COURIER TRACKING MANAGEMENT SYSTEM
State Machine Diagram
============================================================

PURPOSE AND TYPE
- The object is one courier parcel. The diagram records how its tracking status changes.

STATES AND TRANSITIONS
- The initial node enters Booked when shipment booking is created.
- Booked means the shipment is registered but pickup has not happened.
- pickup done moves it to PickedUp.
- reaches hub moves it to Sorting, where the parcel is organized for routing.
- sorted and dispatched moves it to Dispatched for transport.
- reaches destination hub moves it to OutForDelivery in this simplified model.
- OutForDelivery means a delivery attempt is underway.
- delivery successful moves it to Delivered.
- recipient unavailable moves it to DeliveryFailed.
- retry delivery returns it to OutForDelivery.
- max attempts reached moves it to Returned.
- Delivered and Returned lead to the final node.

EXAMPLE AND VIVA
- A parcel is booked, picked up, sorted and dispatched. The recipient is unavailable on the first attempt. A retry succeeds, so the parcel becomes Delivered.
- Begin with this explanation. This state machine follows the parcel from booking to delivery and includes retry and return paths when delivery is unsuccessful.
- Returned is a simplified terminal status. A detailed courier system can separate Return Initiated, Returning and Returned to Sender.
- The diagram does not show every intermediate hub. Additional transport cycles can be added without changing the basic purpose.

20. ONLINE BUS RESERVATION SYSTEM
Sequence Diagram
============================================================

PURPOSE AND PARTICIPANTS
- This diagram shows interaction order for bus search, seat selection, payment and ticket booking.
- Passenger makes the booking. Reservation System coordinates it. Bus Operator supplies bus and seat information. Payment Gateway processes payment.

MESSAGE FLOW
- searchBuses(source, destination, date) supplies the journey.

============================================================
COMMON VIVA QUESTIONS
============================================================

Why use different UML diagrams for the same system?
- Each diagram describes a different view. Use cases show services and roles, classes show structure, activities show workflow, states show a lifecycle, and interaction diagrams show messages.

What is the difference between an actor and a class?
- An actor is an external role that interacts with the system. A class describes a type of object in the model. A role called Customer can appear as an actor in one view and a Customer class can store customer data in another view.

What is the difference between include and extend?
- Include requires the included behaviour as part of a use case. Extend adds behaviour under a condition to a base use case that is otherwise meaningful.

What is the difference between an activity and a state?
- An activity action describes work being done. A state describes the condition of an object. Verify payment is an action. PaymentFailed is a state.

What is the difference between sequence and communication diagrams?
- Both show interactions. Sequence emphasizes time vertically. Communication emphasizes the connected participants and uses numbered messages for order.

What is the difference between a decision and a merge?
- A decision chooses between outgoing paths using guards. A merge brings alternative incoming paths together. A merge does not synchronize parallel flows.

What does 1 to 0..* mean?
- One object on the 1 side can be associated with zero or many objects on the 0..* side. Each object on the many side is associated with exactly one object on the 1 side.

Does showing a balance check guarantee a safe money transfer?
- No. The result must control whether debit happens. Debit and credit also need atomic execution and error handling in the implementation.

Does a diagram need every possible real-world exception?
- No. Its scope should match the question. However, explicit required alternatives must be included, and simplifying assumptions should be explained rather than treated as universal rules.
